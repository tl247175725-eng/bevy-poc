# Opus 4.8 — 第三次审查：软件工程流程是否合格

> 审查对象：CLAUDE.md / check-iron-law.sh / handoff 模板 / handoff-execution.md / FACT.md / git hooks / ci.yml。
> 审查方法：不只读文档，而是逐个验证"这道闸门在真实代码上到底会不会拦住违规"。
> 结论先行：**这是一套"仪式成熟、产出不成熟"的流程。形式比 95% 的业余项目正规，但几乎所有闸门拦的是"拼写"而不是"语义"，而且有两处闸门是 fail-open（形同虚设）。**

---

## 一、总判断

| 维度 | 判断 |
|---|---|
| 能否保证持续的**代码纪律**？ | **部分能。** 保证了风格/句法纪律（常量集中、禁词不出现、小 diff）。**不**保证语义/行为纪律；甚至因为两处 fail-open bug，连"本地编译/测试必过"都不保证。 |
| 是否**成熟**的软件工程流程？ | **形式成熟，效果不成熟。** Hooks + CI + 模板 + 单一数值源 + 小 diff 是真流程。但闸门大多是 proxy，有两处直接失效，且 if-else 检查看不见它自己点名要抓的反模式。 |
| 是否**避免了关键技术债**、让迭代/加内容成本极低？ | **避开了一类，养大了最贵的一类。** 数值重复、type_name 蔓延、大 diff 控制得好。但恰恰因为没有任何闸门测"功能"，项目积累了最昂贵的债——**一个跑不起来却测试全绿的内核**（见第三次审查 review-2）。加"定义"很便宜，加"能跑的行为"完全没有被降低风险。 |

一句话：**这套流程把"通过检查"和"东西能用"之间的等号，悄悄换成了不等号。** review-2 发现整个生态是冻结的，而本次审查证明：**当时所有闸门都是绿的。**

## 二、我实际验证了什么（不是读文档，是验证闸门会不会 fire）

| 验证项 | 结果 | 含义 |
|---|---|---|
| git hooks 是否激活 | `core.hooksPath = .githooks` ✅ | 钩子是真挂上的，不是摆设 |
| 规则1 (禁 `EntityId(0)`) 当前是否绿 | 绿——全仓 `EntityId(0)` 都包成了 `const NONE_ID = EntityId(0)` | **但这正是问题**（见 §3.A） |
| smoke 失败是否会让 CI 失败 | **否。** `smoke_test::run()` 打印 `SMOKE: FAIL` 但**从不 `process::exit(1)`**；`main.rs` 调用后 `return` → `cargo run -- --smoke-test` 永远退出码 0 | CI 唯一的行为闸门**不阻塞** |
| 本地 hook 的 `cargo check/test` 是否真能拦编译错误 | **否。** pre-commit `cargo check 2>&1 \| tail -3`、pre-push `cargo test 2>&1 \| tail -3`，管道退出码取自 `tail`(=0)，且 hook 只 `set -e` 没 `set -o pipefail` | 本地编译/测试失败**不会**阻止 commit/push |
| smoke 的"移动"指标量的是哪套系统 | `e.ecology_state != Idle`——**旧的 reactive 系统**，不是新的 need_match 管线 | smoke 变绿也**不能**证明新架构产出了任何行为 |
| 文档承诺的 clippy 是否在 CI | **否。** workflow 写"编译器自动验证（clippy + test）"，但 `ci.yml` 没有 clippy step，hooks 也不跑 clippy | 承诺与现实不符 |

**这六行是整篇审查的骨架。** 一套流程的成熟度，不看它声明了多少铁律，看它的闸门在违规面前会不会真的红。这里有一半不会。

## 三、致命缺陷（按严重度）

### A. 形式压倒功能——这是缺陷的"母类"

**所有程序化检查验的都是句法/拼写，没有一条验语义/行为。** 最锋利的证据：

review-2 发现 `execution.rs` 里 `Strike { target: EntityId(0) }`——攻击一个幽灵实体 0。本次看：全仓 `EntityId(0)` 已经被改写成

```rust
const NONE_ID: EntityId = EntityId(0);
// ... Strike { target: NONE_ID }
```

规则1（禁裸 `EntityId(0)`，`grep -v NONE_ID`）现在**绿了**。三柱模板**过了**。但 `NONE_ID` 就是 `EntityId(0)`，**Strike 依然打向不存在的实体 0，bug 一字未改。**

> 这就是 Goodhart 定律的教科书现场：指标（"不出现字面 `EntityId(0)`"）成了目标，于是**改个常量名就满足了指标，而指标本该代理的东西（动作要指向真实目标）原封不动。** 流程把一个语义 bug，通过重命名常量，转化成了一次绿色构建。

### B. 唯一的行为闸门既不阻塞、又量错了系统

`memory/FACT.md` 写着铁律："0 移动 / 0 捕猎 → smoke 视为失败"。但：

1. **不阻塞**：`run()` 打印 `SMOKE: FAIL` 却不 `exit(1)`。CI `cargo run -- --smoke-test` 永远返回 0。这条铁律**在管道里是不可执行的**。
2. **量错系统**：移动指标读 `ecology_state != Idle`（被替换中的旧系统），不是 need_match。绿了也不代表新管线动了。
3. **闸门被放水**：捕猎从 failure 降级成 warning（注释"生态刚解冻"）。**当现实过不了闸门时，被改的是闸门，不是现实。** 这是最危险的信号——流程开始为破损状态让路。

### C. 声明的严重度 ≠ 强制的严重度

CLAUDE.md 说"违反 = commit 被拒"，列了禁 unwrap/expect、禁 if-else 标签链。但 `check-iron-law.sh` 里这些都是 `check_warn`（不阻塞）。**只有规则 1/2/4/5/7 是硬失败。** 所以一半"铁律"是剧场——文档威胁的拒绝，脚本并不兑现。

### D. grep 检查脆弱且可绕过，最严重的是"看不见自己要抓的东西"

- **硬编码行号豁免**：规则2 里 `card_def.rs:1[0-9][0-9]`——一旦行号挪动立刻失效（rot）。
- **整文件豁免**：`interaction/recipes.rs` 被整体排除。
- **规则3（if-else 标签链）只匹配单行 `if card_has_tag(...){...}` + else if。** 而 review-2 抓到的真实反模式 `init_animal_knowledge` 里是**多行块**的 `if card_has_tag("diet:herbivore") { ...塞知识... }`——**规则3 根本匹配不到。** 一条以"禁标签 if-else"为名的检查，看不见项目里最典型的标签调用违规。**看不见目标的检查比没有检查更坏，因为它制造虚假安心。**

### E. 没有任何闸门把代码和"生态能跑"这个真目标绑起来

所有闸门都是局部/句法的。没有一条断言："食草动物走到食物边、Consume 在真实目标上触发"、"需求被满足后下降"、"N tick 后种群靠真实生死维持在区间内"。**集成接缝——review-2 发现一切断裂的那个确切位置——恰好是零覆盖的地方。**

### F. 管线空转 / 死代码完全检测不到

`env = Vec::new(); // TODO`、`count_prerequisites_met` 永远返 0、`decomposition: vec![]`、Hydration/Rest 需求从不实例化、13 种 diet 只有 3 种有知识、`tick_starvation` 空函数、`tick_reproduction` 解析旧词表——**没有一条被任何闸门捕获**，因为它们全是"能编译、单测能过的合法 Rust"。`cargo test` 绿是因为单测用 fixture 喂了真实管线永远喂不进去的数据。**没有"热路径禁 TODO/stub"检查，没有"每个 NeedKind 必须在某处被实例化"检查。**

### G. 本地 hook 的 fail-open（具体 bug）

```bash
# .githooks/pre-commit
set -e                       # 注意：没有 set -o pipefail
cargo check 2>&1 | tail -3   # 退出码 = tail = 0，cargo 失败被吞
```
pre-push 的 `cargo test 2>&1 | tail -3` 同理。**结论：本地编译错误和测试回归都不会阻止 commit/push。** 真正能拦测试回归的只剩 CI 的 `test` job（它直接 `cargo test`，没接 tail，是对的）。于是：行为回归只有 CI 抓得到，本地抓不到；而行为本身（smoke）CI 也不阻塞。**唯一真盾是 CI 的单测——而单测因为 fixture 全绿。**

## 四、逐个回答你的四问

**Q1. 能否保证持续的代码纪律？**
能保证**句法纪律**（数值集中在 `meta_values.rs`、禁词不现身、每次 ≤2 个 .rs、handoff 三段式）。**不能**保证语义纪律。而且因为 §3.G 的管道 bug 和 §3.B 的非阻塞 smoke，连"提交的代码一定编译过、测试过、能动"都保证不了。纪律是真的，但它管的是格式，不是正确性。

**Q2. 是否成熟的软件工程流程？**
**结构上：是。** core.hooksPath 激活的钩子 + 分层 CI（iron-law → test → smoke）+ 强制 handoff 模板 + 单一真相源 + 小 diff 纪律 + 技术前提验证规则——这套组合拳在独立/业余项目里属于上游。
**效果上：不是。** 它是"看起来成熟"的流程：闸门多为 proxy，两处 fail-open，checker 对头号反模式失明，声明严重度与强制严重度脱节，CI 缺它自己文档承诺的 clippy。成熟流程的标志不是闸门数量，是"闸门会在真违规时变红"——这里一半不会。

**Q3. 是否避免了关键技术债、让迭代/加内容成本极低？**
**避开了一类，养大了最贵的一类。**
- 避得好：数值重复（规则4/5）、type_name 蔓延（规则2）、大 diff 爆炸半径（pre-push ≤2 文件）。加**定义**（卡/标签）确实便宜——`tags.ron` + registry 是真资产。
- 养大了：**"跑不起来却全绿"是这个项目最贵的债**，而它能长这么大，正是因为没有任何闸门测功能。"加内容成本低"有一半是错觉：加定义便宜，**发现这些定义没接上**很贵——要靠人深读两轮 review 才暴露。低成本是把成本推迟、藏起来了，不是消除了。

**Q4. 有没有该补但没考虑到的检查/流程？**
有，见第五节。最关键的一条：**目前没有任何一个闸门会因为"生态不动"而变红**——而这恰恰是项目唯一真正重要的属性。

## 五、应当补充的检查与流程（按优先级，可直接落地）

**P0——不修这三条，其余都是装饰：**

1. **让 smoke 阻塞。** `run()` 末尾：`if !failures.is_empty() { std::process::exit(1); }`。一行。没有它，FACT.md 的"0移动→失败"铁律是空文。
2. **修 hook 的 fail-open。** 去掉 `| tail -3`，或在 hook 顶部加 `set -o pipefail`，或直接 `cargo check || exit 1`。否则本地两道闸门都漏编译/测试错误。
3. **加一个跑真实管线的集成测试（`tests/`），断言行为而非结构。** 生成真实世界 → 跑 N tick → 断言：(a) 至少一次 `Consume` 触发在**真实**目标上（target ≠ NONE_ID 且实体存在）；(b) 某动物吃后 Nutrition need 实际下降；(c) 种群靠真实出生+死亡维持在区间；(d) 至少一个实体经由 need_match（而非 ecology_state）移动。**这个测试就是会在 review-2 第一秒抓到整个崩溃的那道闸门。**

**P1——堵住"改名绕过"和"死管线"：**

4. **语义化 NONE_ID 禁令**：非测试代码中禁止把 `NONE_ID` 作为 `Strike/Consume/Combine` 的 target（堵住 §3.A 的重命名漏洞）。
5. **"热路径禁 stub"检查**：grep `main_tick.rs`/`need_match/`/`execution.rs` 里的 `Vec::new(); // TODO`、`todo!()`、命名为 `*_met`/`count_*` 却恒返 0 的函数。
6. **覆盖性测试**：断言"每个 `NeedKind` 在 `init_animal_needs` 的某条路径上会被实例化"（抓 Hydration/Rest 死需求）、"每个 `diet:` 标签在 `init_animal_knowledge` 有对应分支"（抓 13 选 3 的洞）。

**P2——把"看起来严"变成"真的严"：**

7. **强化规则3**：用多行/`-A` 上下文匹配 `if card_has_tag(...) { ...块... }` 的标签调用模式，或改为硬失败 + 显式 `// IRON-LAW-ACK: 理由` 才放行。现状是它看不见 `init_animal_knowledge`。
8. **对齐声明与强制**：要么把 unwrap/expect/标签 if-else 改成 `check_fail`（硬失败），要么别在 CLAUDE.md 叫它们"commit 被拒"的铁律。文档不该威胁脚本不兑现的惩罚。
9. **把硬编码行号豁免换成 inline 标注**（`// iron-law:allow type_name=本地化显示`），让豁免不随行号 rot。
10. **CI 补 clippy**：`cargo clippy --all-targets -- -D warnings`。文档已经承诺了，补上即可，顺手把 fail-open 的 unwrap 风险也收一部分。

**P3——流程环节（不是脚本，是规矩）：**

11. **纵切闸门（呼应 review-2）**：在 smoke 于一条真实闭环上变绿之前，禁止新增任何卡/标签/元动作。可机械化：CI 统计卡数 vs 一个 `loop_proven` 标志文件，卡数增长但标志未置 → 失败。这是把"抵抗本体论引力"写进流水线。
12. **smoke 增加确定性回归基线**：固定 seed + 种群轨迹 golden snapshot + 多 seed 跑。当前单 seed、1000 tick、`30<count<900` 的宽松区间，是非常弱的生态健康信号——它能容忍"完全冻结"和"剧烈崩溃"两种截然相反的病态。
13. **handoff 验收段补一条强制项**：`[ ] 我亲眼/亲测确认了本改动让某个行为端到端发生（附 smoke 输出或集成测试名）`。现在的"智能验收"四项仍是句法层；review-2 的崩溃正是因为"读 diff 查 4 条"查的还是同样的句法。

## 六、结语

这套流程的**意图**是顶级的：三柱本体、单一数值源、小 diff、技术前提验证、debt 台账——设计者显然认真读过软件工程，且比绝大多数人更自律。问题不在动机，在**闭环**：

> 几乎每一道闸门都在测"代码长得对不对"，没有一道在测"世界动不动"。于是流程可以长期保持全绿，而内核可以长期不能跑——这两件事在当前流水线里**不矛盾**。

最危险的征兆不是某条规则弱，而是 **§3.B 那次"把捕猎从 failure 降级为 warning"**——当现实撞上闸门，被调整的是闸门。一套流程一旦开始为破损状态让路，它就从"质量护栏"退化成"绿灯生成器"。

如果只能改一件事：**让 smoke 阻塞，并让它测新管线产出的真实行为（P0 的 1+3）。** 在那之前，所有"全部通过 ✅"都只是关于格式的陈述，不是关于这个游戏的陈述。

——架构能成（见 review-2）。流程的形也对。但流程现在守的是字母，不是精神。把秤砣从"拼写"挪到"行为"，这套流程就能真正配得上它的野心。
