## 零、先说三件你们七个 AI 大概率没看见的事

这三件事不在你们的问题列表里，但它们决定了问题列表里一半的答案是否成立。

### 0.1 致命前提错误：这个模拟根本不在 Bevy ECS 里

你们的 Q3、Q5、Q6 全部假设"元动作/需求/实体在 Bevy ECS 中"。**它们不在。**

真实架构是：
- 整个模拟是一个**单体结构体** `WorldState`，实体住在 `HashMap<EntityId, Entity>` 里。
- 推进方式是一个**普通函数** `main_tick(world: &mut WorldState, delta)`，由唯一一个 Bevy system `advance_sim_ticks` 调用 `sim.0.tick_once()`。
- Bevy ECS **只**承载渲染/输入/UI（`CardVisual`、`grid_render`、`ui_interaction`、`plugins`）。模拟实体**不是** ECS entity，没有 Component，不进 Bevy 的 World，不被 Bevy 的 System 调度。

这意味着 Q3 的选项 (a) System-per-action、(b) Action-as-Component **在当前架构下都不可能**，除非你先把整个模拟层从 `HashMap<EntityId, Entity>` 迁移进 Bevy ECS——那是一次推倒重来的全量重写，而你们的问题清单里没有任何一条承认这个工作量的存在。这是最大的暗礁：你们在为一个不存在的 ECS 架构做架构设计。

正确的判断是：**模拟层应该继续留在 `&mut WorldState` 之外，不要进 ECS。** 200 实体的 HashMap 模拟用 ECS 一点好处都没有（没有并行收益、没有 archetype 收益），却要付全量重写的代价。元动作的执行模型只能是 (c) 的变体：纯函数序列，由 `tick_once` 内部的解释器循环驱动。详见 Q3。

### 0.2 "单一数字来源"已经自相矛盾

铁律说"所有数字追溯 `meta_values.rs`"。但：
- `design-philosophy-v5.md` 第 165 行：`1 day = 480 tick @ 2 tick/s`
- `design-philosophy-v5.md` 第 339 行：`1 day = 420 tick`（标注"铁律"）
- `meta_values.rs` 实际计算：`2 × 60 × 60 × 24 = 172800`，且有测试 `assert_eq!(TICKS_PER_DAY, 172800)` 锁死。

**同一个量纲，三个互相矛盾的"真理"，相差 400 倍。** 而且 `FACT.md` 说"无 HP"，`design-philosophy-v5.md` §8.2 却写"hp（工程保留）"，`meta_values.rs` 有 `BASE_HP=1`，`Entity` 有 `hp: i32`。你们的"铁律"层本身就不闭环。在这种状态下谈"数字可追溯"是空中楼阁——追溯到的源头自己在打架。

### 0.3 `EntityProfile` 是你们想删的东西的藏身处

设计说"实体只有标签"。但真实代码路径是：`tags: Vec<String>` → `build_profile()` → 一个有 20+ 个**强类型字段**的胖结构体（size / native_medium / bridges / channels / drives / needs / social_structure / height / ...）。每个字段都是对特定标签前缀的**硬编码解释**（`parse_native_medium`、`parse_bridges`、`parse_drives`、`parse_needs`、`parse_height`...）。

**你们想消灭的"字符串匹配 if-else 行为链"并没有消失——它从运行时搬到了解析期，藏进了 `parse_*` 函数群里。** `EntityProfile` 就是行为链的物化缓存。换位掩码删不掉它（见 Q4），因为位掩码只能表达"有没有 vision"，存不下 `vision(r=6)` 里的 6。

## 一、致命级

### Q1. 公理引擎兼容性

**判断：四条公理的"数学公式"可全部复用，"输入契约"必须重写。type_name 硬编码不是主要问题，`EntityProfile` 才是。**

- `compose` / `traverse` / `perceive` / `transform` 四个函数体内部的**计算逻辑是干净的纯函数**，值得保留：传导率取 min、有效距离 = range × keen × visibility × conduction、能量 = drawn × efficiency。这些公式与现实结构同构，是这个项目里少数真正达到设计哲学 §6.1 标准的代码。
- type_name 硬编码只有**两处、共两行**：`laws.rs:38` 的 `ends_with("Corpse")` 和 `build_profile` 接受 `type_name: &str`。这是最容易修的部分——`is_corpse` 早已是 `Entity` 的字段，`ends_with("Corpse")` 是冗余兜底，删掉即可。把它当"致命"是高估了。
- **真正要重写的是 `EntityProfile` 的地位**。它现在是"一次解析、到处复用"的反规范化快照。在全标签化架构里，它要么被废弃（公理直接读标签集 + 参数侧表），要么被降级为"参数侧表"本身（见 Q4 关于参数化标签的判断）。我的判断：**不可能完全废弃**——只要存在 `need:eat(rate=0.5)` 这种带数值载荷的标签，你就需要一个解析后的结构来装那个 0.5，那个结构就是 `EntityProfile` 的转世。诚实的做法是把它瘦身改名为 `ParsedParams`，承认它的存在，而不是假装全标签化之后它会消失。

### Q2. Entity 去 HP 化

**判断：删 `hp` 是 5% 的工作，删那 40 个布尔状态位才是 95%。EcologyState 该删，但删了之后真正的难题不是 HP。**

- `Entity` 有约 45 个字段，`hp: i32` 只是其中一个。把 hp 换成 vital 标签 + 材质属性，这一步孤立看很简单。
- 难的是 `in_den / in_tree / in_pool / in_ground / in_burrow / in_cover / hidden_in_grass / host_tree_id / host_cover_id / host_pool_x/y / carrying / den_id ...` 这一大坨。它们编码的是 **Hide/Emerge 的执行残留状态**和**空间例外状态**，而 `compose`/`perceive` 直接依赖它们（`entity_occupies_active_cell` 读 `in_pool`/`in_tree`/`in_cover`）。
- 设计说"元关系 = 元动作执行后的残留标签"。但"这只兔子此刻藏在那丛灌木（实体 47）里"是一个**带目标引用的关系**。扁平标签集存得下"hidden"这个质性，**存不下"47"这个目标 ID**。所以你要么引入带目标的关系边（结构化数据，不是标签），要么把 ID 编码进标签字符串（回到字符串匹配）。**这是 Q2 的真正裂缝，不是 HP。** "标签即后果"在需要"后果指向某个具体实体"时失效。
- `EcologyState` 枚举（Idle/Seeking/Fleeing/Hunting/...）：**应该删，且已经在掏空进程中**（`tick_reactive` 已归零）。它就是设计哲学 §3.1、§5.4 明令禁止的状态机。这点我同意你们。但注意：它当前仍是 `Entity` 的字段且被 `lib.rs` 导出、被 smoke_test 间接依赖，删它会牵动一串编译错误。

### Q3. 元动作 ECS 执行模型

**判断：问题本身基于错误前提（见 0.1）。正确答案是 (c) 的变体，且 (a)(b) 在不重写整个模拟层的前提下不可实现。**

- 模拟不在 ECS 里。元动作没有 Bevy System 可挂，没有 Component 存储可用。
- 唯一现实的模型：元动作是**对 `&mut WorldState` 操作的纯函数/小函数**，每个实体在 `tick_once` 内被一个解释器循环消费一段"元动作序列"（`Vec<MetaAction>`）。`MetaAction` enum（现 8 变体）就是这个序列的元素——这是它当前正确的设计方向，保持它是数据（enum），不要把它变成 Bevy Component。
- **Elapse / Chance 的判断你们是对的**：它们不是实体发起的，是世界被动推进。它们的正确位置就是 `main_tick` 顶层的几行（`tick_count += 1`、weather/decay 推进、RNG 结算），而这**恰恰已经是现状**（`sim_clock.tick_time_weather`、`batch_uniform`、`flush_corpse_decay`）。Elapse/Chance 不需要进元动作分发，它们是 tick 循环的骨架。这部分架构现在是对的，别动它。
- 唯一要警惕的：如果哪天有人为了"用上 Bevy"把模拟实体迁进 ECS，那一刻这个项目的确定性、可测试性、单线程可重放性会全部付之东流，换来的是 200 实体根本用不上的并行。**坚决不要。**

### Q4. 标签系统最优实现

**判断：位掩码能解决质性层（boolean 标签），解决不了参数层（带数值的标签）。这是你们方案里没被讨论的断层。学习与编译期注册的矛盾是小问题，参数化标签才是大问题。**

- 位掩码 `[u64; N]` + 父位含子位 + 一次 AND 做子树检查：对**纯布尔标签**（`predator`、`body.large`、`grass`）完全成立，是正确方向，比现在 `t == tag || t.starts_with("{tag}.")` 每次 `format!` 分配字符串强一个数量级。
- **但你们至少一半的标签不是布尔的**：`need:eat(rate=0.5,curve=steep)`、`sense:vision(r=6,acuity=high)`、`meat_yield:3`、`drive:seek(target=foodSource,range=6)`、`height:flat`、`material:iron`（背后是密度/硬度数据库）。位掩码能表达"这实体有 vision 能力"O(1)，**存不下 r=6**。所以每一个参数化标签都还需要一张侧表（`HashMap<EntityId, ...>` 或解析后的结构体 = `EntityProfile` 重生）。**位掩码方案只覆盖了冰山水面上的部分。** 设计哲学 §1.2 说"数值不写在标签上，从标签组合推导"——但 `need:eat(rate=0.5)` 里的 rate=0.5 就是写在标签上的数值，它无处可推导，只能存。设计原则和标签实际形态在这里直接冲突。
- 学习（运行时新增标签）vs 编译期位掩码：**这其实是小问题。** 编译期注册的是"已知标签宇宙"的位分配。运行时学习一个**已注册但之前没有的标签**（"红果子→有毒"用的是已注册的 `toxic` 位）→ 只是 set 一个 bit，零矛盾。只有学习一个**全新的、世界本体里从未定义的概念**才需要动态扩展位空间——而生态模拟里几乎不会发生这种事（动物不会发明新的物理质性）。所以保留少量"动态标签溢出区"（超出 `[u64;N]` 的部分用一个小 HashSet 兜底）就够了，不必为此否定位掩码。
- 调试/序列化：位掩码反而**更好**序列化（定长字节），存档稳定。中文显示和审计需要一张 `Tag → 中文 / Tag → 维度` 的反查表，从同一份 `tags.ron` 编译期生成——这比现在 `tag_zh.rs` 417 行的字符串前缀汤更健壮、更不容易漏注册。Q8 会再说。

## 二、严重级

### Q5. 需求匹配数据结构

**判断：又是被 0.1 误导的问题。没有 Component 可用。需求是 `Entity` 的字段或 `WorldState` 的侧表，知识图是 per-entity 的 map，三层过滤是同一函数内的阶段而非独立 System。**

- "need 是 Component 还是 Resource"——既不是，因为模拟不在 ECS。need 是 `Entity` 上的一个字段（现在已经有 `needs: SmallVec<[NeedState;4]>` 在 `EntityProfile` 里，这是对的雏形）。
- 知识图：**应该是 per-entity 的**（`HashMap<Tag, KnowledgeEntry>` 挂在 Entity 上或一张 `WorldState.knowledge: HashMap<EntityId, ...>` 侧表）。**不能是全局 Resource**——全局知识图等于"全族瞬间共享认知"，那就消灭了 Teach 的意义，也消灭了 Q7 里"试错学习"的全部生态张力。
- 三层过滤（功能→可行性→风险）：**同一个函数里的三个 `filter` 阶段**，不是三个 System。把它们拆成三个 System 只会制造跨 System 的中间状态传递成本，且在非 ECS 架构里根本没有 System 可拆。
- 基线计算（`baseline = metabolism × mass × species_factor`）：**启动时预计算存进字段**。这是不随 tick 变化的常量，每 tick 重算是纯浪费。它属于"解析期"那一层（又一次指向 `EntityProfile` 不会消失）。

### Q6. 性能瓶颈预判

**判断：200 实体下算法复杂度全部无关紧要。真正的瓶颈是字符串标签的分配/克隆 churn，不是 O(n²)。你们在担心错误的东西。**

- 感知"四通道 × 200 × 15 邻居"：空间索引（bucket grid）已经把它从 O(n²) 降到 O(n × k)，k≈邻格内实体数。200 实体、36×24 格，这是**微秒级**，不会卡。`spatial_index.rs` 的 bucket 实现是这代码库里质量最高的部分之一。
- A* 寻路 200 实体同时跑：曼哈顿网格、36×24=864 格，单条路径最坏几百节点。200 条/tick 也就十万级操作，**不是瓶颈**。
- 知识图匹配：你们自己算的 250 次标签比较——**可忽略**，对。
- **真正的瓶颈**：每次 `build_profile`/`reindex_entity`/`spatial_index.insert` 都在 `clone()` 一整个 `Vec<String>`（`tags: Vec<String>`，`by_tag: HashMap<String, HashSet>`），`card_has_tag` 每次调用 `format!("{tag}.")` 堆分配一个新 String。在 1000-tick smoke 里这是**持续的 allocator 压力 + 缓存不友好的指针追逐**。smoke_test 的 `max_tick < 15ms` 阈值如果哪天飘红，凶手是这个，不是寻路也不是感知。换位掩码（Q4）真正的收益不在算法复杂度，而在**消灭这一层 String churn**。这是该提前准备的优化，且它和 Q4 是同一件事。

### Q7. 知识图"玩"发现失控

**判断：会膨胀，但膨胀不是真问题。真问题是这个学习机制本身是致命的、且不可共享——它会在学会之前先把种群杀光。遗忘机制是治标，Inherit 播种 + 死亡观察学习才是治本。**

- 垃圾知识膨胀：是的，200 实体各存 100 条"X 不可吃"会涨。但每条目几十字节，200×几百条 = MB 级，**内存不是瓶颈**。
- **被你们忽略的致命点**：B 方向搜索"感知红果→不知道→Combine→Consume→中毒"意味着**每个知识点的获取代价是一次濒死或真死**。现实生态里动物绝大多数毒物不是靠试错学会的——是**靠 Inherit 继承回避**（基因写入"别碰这个气味"）或**靠观察同类死亡社会学习**。你们的架构有 Inherit 元动作，但没说 Inherit 会播种知识；有 Receive/Process，但没说"看见同类吃 X 后死"会写入"X→危险"。**缺了这两条，纯试错的 B 搜索会让种群以远快于学习速度的速率死亡**——你会得到一个"刚出生就饿死或毒死"的世界，而不是一个学习的世界。
- 所以：遗忘/衰减（memory_decay 你们 A 层已列）是需要的，但它解决的是"陈旧知识"问题，不是"垃圾爆炸"问题。**优先级反了**：先让 Inherit 播种初始回避知识 + 让死亡可被观察学习，再谈遗忘。否则你优化的是一个还没活到能膨胀就已经灭绝的系统的内存。

### 一个你们没问但很重要的状态事实

## 三、重要级

### Q9. 实现顺序

**判断：依赖图决定顺序，且第 0 步必须是重定义验收门，否则你从第一步就是红的。**

依赖关系（谁需要谁先存在）：
- 需求匹配引擎(e) 需要 meta_values(b) 和 tags(a) 都就位——它引用数值和标签。
- 公理去 type_name(d) 在确定标签表示(a) 之前没法真正做干净。
- meta_action enum(c) 廉价且独立。

因此顺序：
0. **重定义验收门**（最先，否则全程红灯）：把"必须有捕猎"的 smoke 换成一个能在纯化态增量满足的最小目标——比如"1 种食草卡 + 1 种食物卡，食草卡能通过需求匹配走向并 Consume 食物"。没有这一步，你们在第 1 步就被锁死。
1. **(b) meta_values 扩展**。纯常量，零行为风险，解锁一切，且直接修复 0.2 的三值矛盾（先把 1 day = 几 tick 定死成一个数）。这是唯一能"一次改对、永不回头"的基础层。
2. **(a) 标签位掩码——但只做布尔层 + 同时定下参数侧表的方案**（Q4）。不解决参数化标签就上位掩码 = 半截子工程。
3. **(d) 公理去硬编码**。此时变成两行删除 + 公理读位掩码，trivial。
4. **(c) 25 元动作 enum**。数据定义，独立。
5. **(e) 需求匹配引擎**。最后，因为它依赖前面全部。

不要先做 (e)。需求匹配引擎是塔尖，在地基（数值+标签）未定型时写它，等于在流沙上盖楼，每次改标签表示都要重写匹配逻辑。

### Q10. 超自然 Create/Destroy 与公理兼容

**判断：Create 必须过 compose 否则破坏"一格一卡"；一旦给它开 override，公理的"纯函数、输入相同输出相同"不变式就被击穿——这是真实张力，不能两全。Destroy 在 causality 里留悬空 u64 引用，不崩但污染追溯。**

- **Create vs compose**：被 Create 出来的物体若要进一个已占格，compose 当前会拒（`living_count > 0`）。设计说"超自然 = 公理覆盖"。但 `compose` 现在**没有 override 钩子**，它是纯函数。要让 Create 豁免，你得加一条 `force` 路径——那一刻 `compose(cell, profile)` 的输出不再只取决于 (cell, profile)，还取决于"是不是 Create 在调"，**纯函数性破裂**。这是不可调和的：Create 要么尊重 compose（那它就不是真豁免，只是"找个空格生成"），要么绕过 compose（那公理就不再是合法性的唯一权威）。我的判断：**选前者**——Create 只在 compose 允许的格生成，"无中生有"指的是"无父体"，不是"无视物理空间"。真正的"无视空间"应该极其罕见且走单独的世界级操作，不污染公理层。
- **Destroy vs causality**：`CausalEvent` 存的是 `cause_entity_id: u64` / `effect_entity_id: u64` 裸整数 + String 描述。Destroy 移除实体后，日志里引用它的条目变成**悬空 ID**——不会崩（只是整数），但任何"回溯这个结果的起因"的查询会命中幽灵 ID。加上 `EntityId` 是单调 `next_id` 永不复用，所以不会张冠李戴，但 Ring buffer 模式下因果完整性是**最终一致而非保证**。判断：这是可接受的设计债，**只要因果日志的定位是"调试/叙事"而非"游戏逻辑依赖"**。一旦有任何游戏机制（比如"复仇"需要回溯杀手）依赖因果链，Destroy 的悬空引用就会变成 bug 温床。现在没有这种依赖，所以现在安全；但这是一颗会随社会层（复仇/债务/声誉）落地而引爆的雷。

## 四、检查直觉

### Q11. 最大的逻辑漏洞

**这个体系最大的设计层漏洞：它删掉了"规划"，却保留了大量需要规划才能涌现的目标。它在"反应式"和"深思式"之间精神分裂。**

设计哲学 §3.1 明确宣称："没有'权衡利弊'的步骤。没有'计算得分'的步骤。只有：当前状态 × 需求激活 × 环境匹配 × 执行。" 这是一个**贪心、单步、反应式**的选择器。

但你们的元动作清单和招牌例子需要**多步前瞻**：
- 招牌例子"造篝火 = Combine(树枝, 燧石)" + "cold + can_craft + fire_nearby → 涌现造篝火需求"。可是如果 fire **不在**附近，你得先：找树枝 → 找燧石 → Combine → 在冷且有威胁时点燃。**捡燧石这一步在"不冷"的时刻满足零个即时需求**。一个"覆盖最多急迫需求"的贪心匹配器**永远不会去捡那块燧石**，因为它当下不缓解任何需求。
- `Commit`（面向未来的约束）、`Assign`、工具制造——全部要求"为了未来的回报做当下无收益的事"。这正是规划的定义。
- `Decide`"是'知道'到'去做'的跳跃，生成意向"——但从 Decide 生成的"意向"到"元动作序列执行"之间，**有一个未被任何机制覆盖的排序/规划步骤**。设计哲学明确拒绝放入这一步（§3.1），却又需要它（造篝火/Commit/工具）。**这就是你们要找的 Y→Z 断层：意向 → 序列之间的路径没有被任何元动作或匹配逻辑覆盖。**

结论是二选一，不能既要又要：
- **要么**行为停留在真正反应式（吃草、逃跑、藏匿）——那 25 个元动作、整个心智/社会层是杀鸡用牛刀，绝大多数永远不会被触发。
- **要么**引入真正的规划（哪怕只是 1-2 步前瞻 + 一个小目标栈）——那"没有决策，只有对应"这句话就是假的。

附带一个更隐蔽的洞："叠加域涌现造篝火"被反复断言（"从公理和需求匹配中涌现"），**但从未被机制化**。四条公理里没有一条、贪心匹配器里没有一行，能从 {cold, predator, can_craft, fire_nearby} 产出"build fire"这个**当前世界里可能根本不存在的实体**的构造意图。如果 fire 不在场，就没有东西可匹配。"涌现"这个词在这里承担了大量未兑现的工作。它是信仰，不是机制。

**如果非要我指最弱环节、最可能崩塌的时刻**：就是你们第一次试图让一个实体"造出一个原本不在环境里的东西"（篝火/工具/任何 Combine 产物）的那一刻。在此之前（纯觅食/逃跑生态），反应式架构跑得很好，甚至优雅。在此之后，你会发现需求匹配引擎产出不了多步计划，然后被迫在它旁边偷偷加一个 planner——而那个 planner 就是你们花一周用七个 AI 论证"不需要"的第四根柱子。

### Q12. 一句话：能落地吗

**悬。**

能落地的前提条件，三条，缺一不可：
1. **认清模拟不在 ECS，且坚持不让它进 ECS**（0.1）。否则你们会在某次"用好 Bevy"的冲动里把整个确定性模拟重写进 ECS，换来 200 实体用不上的并行，赔掉可测试性和可重放性。
2. **正面解决"反应式 vs 深思式"的矛盾**（Q11）：要么砍掉需要规划的元动作，要么接受一个有界 planner。"无规划"+"造篝火/Commit/工具"在数学上不能共存。这是哲学债，不是工程债，代码改不动它，只有设计决策能。
3. **承认参数化标签需要侧表，`EntityProfile` 不会消失**（Q4/Q1）：位掩码管质性，侧表管数值。"只有标签、没有解析结构"这个梦，在标签携带数字时不可达。

如果这三条被诚实面对 → **能**，而且会是个相当漂亮的系统，底层公理和空间索引的质量已经证明你们有这个能力。

如果继续用七个 AI 交叉验证理论完备性、却始终不碰第 1 条（ECS 前提）和第 2 条（规划矛盾） → 它会**永远停在"理论完备、从不运行"**的状态。你们现在的纯化态（5 张卡、掏空的 tick、无法满足的 smoke 门）已经是这个风险的早期症状：架构越来越纯，能跑的东西越来越少。

最后一句：这个体系的危险不在于它错，而在于它**美得让人不想验证**。它最该做的下一件事不是再设计一层，而是让一只羊，用需求匹配，走向一棵草，把它吃掉——在真实代码里，通过 smoke。在那之前，所有完备性都是未兑现的承诺。
